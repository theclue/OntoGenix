# OntoGenix

OntoGenix is a human-steered Qt application for independently exploring data and generating candidate OWL ontologies and RML mappings through an OpenAI-compatible model API.

**Important:**
The configured provider must expose a model compatible with the selected native workflow. No particular model family is required.

## Installation

This fork is intended to run in the dedicated `ontology-stack` payload, not
with host-global Python/Qt dependencies. The isolated payload and headless
entrypoint are present as work in progress, but the headless factory route has
not yet been verified end to end; do not install
`requirements.txt` on the host. The native headless entrypoint is
`python headless.py`; the existing GUI entrypoint remains `python -m GUI` inside
that runtime. Configure API values only through the operator-managed runtime
environment; never store real credentials in this repository or an application
`.env` file.

These are the main steps involved in the generation process of an ontology design withing OntoGenix. 

---

### **1. LOAD CSV**

- **Purpose**: This step focuses on importing the CSV dataset and subsequently producing a comprehensive statistical analysis of the dataset.

---

### **2. PROMPT CRAFTING**

- **Purpose**: A step towards the generation of the prompt that guides to the objective high level structure description of the ontology.

---
### **3. ONTOLOGY GENERATION**

- **Purpose**: The main objective here is to construct the ontology. This will be done through a sequence of structured sub-steps:

---

### **3.1. DESCRIPTION**

- **Purpose**: Two primary tasks will be carried out:
  - Provide a concise summary of the dataset using natural language.
  - Offer a high-level summary of the suggested ontology design architecture.

- **Options**:
  1. Allow the model to suggest a structure.
  2. Manually provide a prompt to specify the ontology's overarching structure.

---

### **3.2. ONTOLOGY**

- **Purpose**: This step is pivotal for creating the ontology's OWL definition, with a spotlight on classes and their associated object and data properties.
  
- **Note**: This process is automatic and doesn't require a prompt.

---

### **3.3. ONTOLOGY_ENTITY**

- **Purpose**: Tailored to formulating the ontology's OWL definition for specific entities.
  
- **Important**: A carefully crafted prompt that vividly describes the task is essential for this step.

---

#### **Examples for Crafting Prompts**:

**Example 1**: Improving a Class

**prompt:**  
Ensure you meticulously follow the guidelines laid out in the data description.
Explicitly reference all object and data properties linked to the entity in question.
Object property restrictions? Always use the "onClass" parameter.
Data type property restrictions? The "onDataRange" parameter is your go-to.
All the above-mentioned tasks should be executed for the entity: `{EntityName}`

---

**Example 2**: Enhancing Object/Data Type Properties

**prompt:**  
Enrich the entity with metadata and annotations to provide context, trace origin, and deliver deeper insights.
Retain the foundational name of the entity.
Include a descriptive field. Consider suggesting an alternative name and provide up to five alternative labels for enhanced clarity and versatility.
If there are any known equivalent properties in the ontology, be sure to define them. Steer clear of inventing fictional ones.
All these tasks are to be done for the entity: `{EntityName}`



---

### **4. MAPPING**

- **Purpose**: In this phase, a mapping is created by making use of the ontology in conjunction with the original CSV dataset.

- **Note**: This process is automatic and doesn't require a prompt.

## Independent candidate workflow adaptation

This authorized local fork runs the original Qt workflow as an independent,
bottom-up candidate generator. It is not seeded from an approved ontology,
competency questions, foundation mappings, or desired workflow conclusions. Its
Turtle/RDF/XML exports remain candidate artifacts for human review; they are
not source evidence or canonical project ontology. The existing project
pipeline can review them against already approved scope/CQs later, without
automatic merging or mappings.

The GUI makes no model request when it opens or resets. Before each provider
request it displays the exact text context and, for image requests, a preview;
provider disclosure requires an explicit confirmation. A second confirmation
precedes each model-selected local GUI action. These confirmations do not
approve ontology scope, CQs, or domain semantics. CSV preprocessing operates on
a private working copy inside the user-owned session directory; the selected
source file is left unchanged. Search is disabled unless
`ONTOGENIX_ENABLE_WEB_SEARCH=1` is explicitly configured, then each query also
requires confirmation. Configure `SERPAPI_API_KEY` only for that opt-in. The
Mermaid preview also discloses its generated diagram to `mermaid.ink` only after
a separate confirmation.

Model selection accepts any non-empty OpenAI-compatible alias. Precedence is
`--api-model` / `-am`, then `ONTOGENIX_API_MODEL` or `OPENAI_MODEL`, then the
existing OpenAI-compatible `default` alias. OpenAI-compatible calls accept
`OPENAI_BASE_URL` and require `OPENAI_API_KEY`. Azure configuration uses the native `--client azure` flag with
`AZURE_OPENAI_ENDPOINT`, `OPENAI_API_VERSION`, and either
`AZURE_OPENAI_API_KEY` or `OPENAI_API_KEY`; `AZURE_OPENAI_DEPLOYMENT` optionally
selects its deployment. No model weights are trained or fine-tuned. Prompt
customization is limited to the trusted plaintext prompt files under `GUI/`;
these files are loaded as text, not executed as plugins.

## Native headless candidate mode

The native `headless.py` entry point is for the stack's authorized bottom-up
candidate workflow; it does not start Qt or the GUI. It accepts only
`--request - --output-dir PATH`, reads the closed request JSON from stdin, and
uses the exact pre-provisioned private session path. It creates a mode-0600
private CSV copy, profiles at most 100 rows and 64 columns without sending raw
rows, then writes `data-profile.json`, candidate `candidate.ttl`, and
`result.json`. The fixed ontology prompt and profile are the only model input;
scope/CQ references are provenance only. Each request is bound to its source
digest, purpose, resolved model alias, request/input/token limits, and deadline;
missing or mismatched authorization fails closed before model dispatch. Output
remains an unapproved candidate for downstream human review, not canonical
ontology. Static command help is available with `python headless.py --help`.
These source-level contracts do not establish that the stack's tool-to-native
factory route or provider-budget enforcement has passed end-to-end verification.
